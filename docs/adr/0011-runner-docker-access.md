# ADR-0011: Доступ раннера к Docker — DinD vs docker.sock

- **Статус:** Принято
- **Дата:** 2026-11-23

## Контекст

Worker должен запускать per-tool контейнеры анализаторов (ADR-0005). Есть два типовых способа
дать контейнеру возможность поднимать другие контейнеры.

## Решение

Выбран вариант **B — монтирование `/var/run/docker.sock`**: `worker` (и/или `runner`) получает
доступ к хостовому Docker-демону. Для внутреннего однопользовательского режима (ADR-0008) это
самый простой и быстрый путь; компонент `runner` как отдельный DinD-сервис не выделяется.

Обязательные меры снижения риска (см. «Последствия»):

- контейнеры анализаторов запускаются **non-root**, с монтированием только рабочей директории
  и без лишних capabilities (`--privileged` для анализаторов не выдаётся);
- сеть анализатора по возможности `none`, доступ к хосту ограничен;
- `worker` сам не выполняет недоверенный код — только оркестрирует контейнеры.

## Альтернативы

- **A. DinD (`docker:dind`)** — изолированно от хоста, но тяжелее, требует `privileged` и отдельного
  сервиса; отклонено для v1 в пользу простоты.
- **Внешний раннер-демон** — избыточно для v1.

## Последствия

- (+) Проще docker-compose, без DinD-сервиса и сетевой настройки; быстрее старт анализа.
- (−) Расширенная поверхность атаки: контейнер с доступом к `docker.sock` фактически равен root на
  хосте. Компенсируется тем, что сервис внутренний (ADR-0008), анализаторы non-root и без привилегий.
- При выходе на мультиарендность/внешний доступ (v2) — пересмотреть в сторону DinD или отдельного
  изолированного раннера.
