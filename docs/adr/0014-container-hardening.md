# ADR-0014: Минимальные привилегии контейнеров

- **Статус:** Принято
- **Дата:** 2026-11-24

## Контекст

После отказа от Docker-сокета (ADR-0011) сервис всё равно запускает недоверенный код анализа
в контейнере `analyzer`. Нужно ограничить возможности контейнеров, чтобы компрометация
анализатора или API не давала лишних привилегий.

## Решение

- Для `api`, `worker`, `analyzer`, `web`: `security_opt: no-new-privileges:true` и `cap_drop: ALL`.
- `web` использует unprivileged-образ nginx (`nginxinc/nginx-unprivileged`), слушает 8080;
  root и `CAP_NET_BIND_SERVICE` не требуются.
- Наружу публикуются только `api`, `web`, `neo4j`; PostgreSQL и Redis — только внутри compose-сети.
- Docker-сокет не монтируется; анализаторы работают внутри выделенного контейнера `analyzer`.
- GitLab-токены шифруются, ошибки клонирования редактируются.

## Альтернативы

- Оставить контейнеры с полным набором capabilities — проще, но шире поверхность атаки.
- Rootless-режим Docker/подов — вне рамок docker-compose v1; отложено.

## Последствия

- (+) Существенно меньше возможностей у скомпрометированного контейнера.
- (−) Образы, которым нужны capabilities (postgres/neo4j), не ограничиваются — это upstream-образы.
- (−) unprivileged nginx меняет внутренний порт на 8080 (внешний порт остаётся `WEB_PORT`).
- При добавлении новых сервисов — проверять, что они работают без capabilities.
