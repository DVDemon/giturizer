# ADR-0011: Взаимодействие worker ↔ analyzer — очередь + общий volume

- **Статус:** Принято (заменяет решение «`/var/run/docker.sock`»)
- **Дата:** 2026-11-24

## Контекст

По [ADR-0005](0005-analyzer-runners.md) анализаторы постоянно работают в выделенном контейнере
`analyzer`. Нужно передать ему клон GitLab-репозитория и забрать результаты, **не** давая доступа
к Docker-демону и не запуская контейнеры на каждый анализ.

## Решение

Взаимодействие через **общую очередь + общий volume**:

1. **Очереди Celery (Redis)**:
   - `pipeline` — оркестрация (`worker`): clone, tech detection, merge, persistence;
   - `analyzers` — выполнение инструментов (`analyzer`).
   `worker` и `analyzer` — отдельные Celery-воркеры, потребляющие свои очереди.
2. **Общий volume `data`** (named volume или bind-mount), смонтированный одинаково в `worker` и
   `analyzer` в `/data`:
   - `worker` клонирует репозиторий в `/data/repos/<run_id>`;
   - `analyzer` читает клон по тому же пути.
3. **Артефакты** — в том же volume: `analyzer` пишет нормализованный JSON в
   `/data/artifacts/<run_id>/<tool>.json`; `worker` забирает его после получения результата задачи.
4. **Нет доступа к `docker.sock`**, контейнеры не запускаются динамически.

Оркестратор ставит задачи анализа **последовательно**: на каждый обнаруженный язык — своя
Celery-задача в очередь `analyzers`, выполнение по одной (`chain`/последовательный `apply_async`
с ожиданием результата). Параллелизм между разными запусками ограничивается `concurrency`
воркера `analyzer`.

## Альтернативы

- **Docker-сокет + spawn контейнеров на анализ** (прежняя редакция) — отклонено.
- **HTTP API в analyzer** — возможно, но очередь уже есть; HTTP добавляет ещё один канал и сервер.
- **`docker exec`** — всё равно требует сокет; отклонено.

## Последствия

- (+) Никакого privileged/сокета; безопасность и compose проще.
- (+) Единая очередь для pipeline и анализа — прозрачный прогресс и ретраи.
- (−) Нужно управлять жизненным циклом общего volume: создание каталога `<run_id>`, очистка
  после завершения (TTL/ретеншн), учёт размера.
- (−) Пути внутри контейнеров должны совпадать (`/data/repos`), иначе analyzer не найдёт клон.
- (−) `analyzer` со слабым `concurrency` — узкое место при многих параллельных запусках.
- (−) Крупные артефакты лучше класть на volume, а не в результат задачи (размер сообщений Redis).
