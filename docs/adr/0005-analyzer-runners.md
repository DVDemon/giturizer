# ADR-0005: Анализаторы в выделенном долгоживущем контейнере

- **Статус:** Принято (заменяет прежнюю редакцию «отдельный образ на каждый анализатор»)
- **Дата:** 2026-11-24

## Контекст

Пайплайн использует разнородные инструменты: ArchGuard scanner (JVM), doxygen + cpp-dependencies
(C/C++ toolchain), pyan + pyreverse (Python), dependency-cruiser + madge (Node). Изначально
планировался запуск отдельного контейнера на каждый инструмент через Docker-сокет. Это требует
доступа worker к хостовому Docker-демону, создаёт накладные расходы (pull/up/teardown на каждый
анализ) и расширяет поверхность атаки.

Новая модель: анализаторы **не запускаются на каждый анализ**, а постоянно работают в выделенном
контейнере `analyzer`, который потребляет задачи из очереди.

## Решение

Один **долгоживущий** контейнер `analyzer` со всеми инструментами анализа, установленными в образ:

- ArchGuard scanner CLI (Java-экосистема);
- doxygen + cpp-dependencies (C/C++);
- pyan + pyreverse (Python);
- dependency-cruiser + madge (Node).

Контейнер `analyzer` работает как Celery-воркер на отдельной очереди `analyzers`:
получает задачу `run_<tool>(repo_path, output_path, options)`, выполняет CLI-инструмент над
клоном репозитория из общего volume (см. [ADR-0011](0011-worker-analyzer-interaction.md)), пишет
нормализованный JSON в общий volume и возвращает в результате задачи путь/статус.

Оркестратор (`worker`) не запускает контейнеры, а ставит задачи в очередь **последовательно**
(по одной на этап анализа), дожидаясь результата каждой.

## Альтернативы

- **Отдельный образ на инструмент, запуск per-run** (прежняя редакция) — изоляция лучше, но нужен
  `docker.sock`/DinD, накладные расходы на запуск и сложнее compose; отклонено.
- **Несколько долгоживущих контейнеров по языкам** — обсуждаемо при конфликтах зависимостей;
  для v1 выбран один контейнер.
- **Внешний ArchGuard-инстанс** — не нужен, scanner CLI покрывает сценарий.

## Последствия

- (+) Docker-сокет не требуется — проще compose и безопаснее (см. ADR-0011).
- (+) Анализаторы прогреты, нет накладных расходов на старт контейнера на каждый запуск.
- (−) «Толстый» образ (JVM + Node + Python + C/C++ toolchain), размер и время сборки растут;
  возможны конфликты версий зависимостей — фиксируем версии инструментов в образе.
- (−) `analyzer` — единая точка отказа для всех анализов; при падении перезапускается, задачи
  остаются в очереди (Celery retry).
- (−) Изоляция инструментов слабее, чем при отдельном контейнере на инструмент.
- При росте числа языков/конфликтов — выделить язык(и) в отдельные контейнеры, очередь и ADR-0011
  не меняются.
