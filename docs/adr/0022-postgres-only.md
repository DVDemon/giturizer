# ADR-0022: PostgreSQL-only — без Neo4j

- **Статус:** Принято
- **Дата:** 2026-11-25

## Контекст

Neo4j использовался для хранения графа и транзитивных Cypher-запросов (ADR-0010).
После удаления UI-графа и публичных `/graph/*` API у Neo4j не осталось читателей:
пайплайн только писал граф, а C4 и JSON-отчёт берут данные из PostgreSQL
(`architecture_snapshots.workspace`/`report`). Двойная запись PostgreSQL + Neo4j
стала лишней.

## Решение

- Полностью убрать Neo4j: сервис из `docker-compose`, драйвер `neo4j`, `NEO4J_*`
  настройки, `services/graph.py`, `graph_writer` в пайплайне, том `neo4jdata`.
- Единственный источник данных — **PostgreSQL**.
- Граф для C4 остаётся в `architecture_snapshots.workspace` (внутренняя модель);
  отчёт — в `architecture_snapshots.report`.
- Данные Neo4j считаются производными и удаляются без миграции: при необходимости
  их можно восстановить из C4-снапшотов.
- Если graph-API понадобится снова, использовать таблицы `graph_elements`/`graph_edges`
  и рекурсивный CTE в PostgreSQL, без Neo4j.

## Альтернативы

- Оставить Neo4j «на будущее» — лишний сервис, память, бэкапы и dual-write без потребителей.
- Перенести граф в отдельные таблицы PostgreSQL сейчас — нужно только при возврате graph-API.
- Apache AGE/pgRouting — расширения не нужны для текущего масштаба.

## Последствия

- (+) Один источник данных: ACID, один бэкап, нет рассинхронизации PostgreSQL/Neo4j.
- (+) Меньше контейнеров и потребление памяти.
- (+) C4/отчёт не затронуты.
- (−) Нет графовых Cypher-запросов; при возврате нужен SQL/CTE.
- (−) Нужно обновить документацию и тесты; миграция схемы не требуется.
