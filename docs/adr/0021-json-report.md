# ADR-0021: Единый JSON-отчёт вместо Structurizr

- **Статус:** Принято
- **Дата:** 2026-11-25

## Контекст

Ранее сервис отдавал `workspace.dsl` и `workspace.json` в формате Structurizr. По новым
требованиям нужен простой машинно-читаемый результат из трёх массивов, без Structurizr-экспорта.

## Решение

Публичный результат запуска — один JSON (`GET /api/runs/{id}/report`):

```json
{
  "technologies": [{"name": "...", "type": "...", "version": "...", "description": "..."}],
  "api": [{"service": "...", "methods": [{"operation": "...", "description": "...", "technology": "..."}]}],
  "deployment": [{"method": "...", "services": [{"name": "...", "image": "...", "image_version": "...", "ports": ["..."], "dependencies": ["..."]}]}]
}
```

- Отчёт собирается после анализа и хранится в `architecture_snapshots.report`.
- Для старых запусков отчёт собирается лениво из технологий/API/deployment и кешируется.
- Публичные `/structurizr*` и `/graph/*` API удалены; C4 использует внутреннюю модель
  (`/c4.model`, `/c4.svg`), наружу Structurizr не отдаётся.
- UI: после завершения анализа верхняя плашка с прогрессом скрывается, остаётся URL + статус;
  в «Обзоре» — статистика запуска, JSON-дерево и скачивание отчёта.

Порядок ключей в ответе: `technologies`, `api`, `deployment`.

## Альтернативы

- Оставить Structurizr и добавить JSON — два конкурирующих формата, лишняя поддержка.
- Хранить только сырые артефакты и собирать отчёт на клиенте — дублирование логики.
- Отдавать JSON без сохранения — дорогая повторная сборка для каждого запроса.

## Последствия

- (+) Простой контракт для интеграций: три массива, без Structurizr-зависимости.
- (+) Меньше публичных API: удалены structurizr и graph-эндпоинты.
- (+) UI показывает отчёт деревом и скачивает одним файлом.
- (−) Внутренняя C4-модель остаётся в БД для вкладки C4.
- (−) Нужна миграция 0007 (поле `report`).
